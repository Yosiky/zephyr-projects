## Текущий урок: 11 — структура в `k_msgq`

### Цель

Сравнить `k_msgq` с `k_fifo` и `k_mem_slab` на сообщениях фиксированного
размера. `k_msgq` копирует всю структуру в свой статический кольцевой буфер, а
значит не требует правила владения динамической памятью.

### Задание

Создайте `11_msgq_struct` и определите сообщение и очередь на четыре элемента:

```c
struct measurement {
    uint32_t sequence;
    int32_t value;
};

K_MSGQ_DEFINE(measurements, sizeof(struct measurement), 4,
              __alignof__(struct measurement));
```

Producer каждые 100 мс формирует измерение и пытается положить его в очередь
без ожидания:

```c
struct measurement measurement = {
    .sequence = sequence++,
    .value = value++,
};

int rc = k_msgq_put(&measurements, &measurement, K_NO_WAIT);

if (rc != 0) {
    dropped++;
    LOG_WRN("Queue full; dropped=%u", dropped);
}
```

Consumer получает сообщение, выводит оба поля и обрабатывает его 1000 мс:

```c
struct measurement measurement;

k_msgq_get(&measurements, &measurement, K_FOREVER);
LOG_INF("Received: sequence=%u value=%d",
        measurement.sequence, measurement.value);
k_msleep(1000);
```

Проверьте, что при медленном consumer появляются пропуски sequence и растёт
`dropped`. Затем замените `K_NO_WAIT` на `K_FOREVER`: пропусков быть не должно,
но producer станет блокироваться, когда очередь заполнится.

### Выбор IPC-механизма

| Требование | Подходящий механизм |
| --- | --- |
| Малые сообщения фиксированного размера, нужна копия данных | `k_msgq` |
| Объекты разного размера, передача без копирования | `k_fifo` + `k_heap` |
| Объекты одинакового размера, предсказуемый лимит памяти | `k_fifo` + `k_mem_slab` |

### Проверка понимания

1. Почему consumer может безопасно изменить локальную `measurement` после
   `k_msgq_get()`?
2. Почему при `K_FOREVER` нет пропусков, но producer может работать реже 100 мс?
3. Почему `k_msgq` не требует `fifo_reserved` и `k_mem_slab_free()`?

## Журнал занятий

### 1–2. Потоки и планировщик — 2026-08-08

- Создано `01_threads` для `qemu_riscv64` с `K_THREAD_DEFINE`.
- Меньшее числовое значение приоритета означает более высокий приоритет.
- `k_msleep()` блокирует текущий поток; равный приоритет не задаёт порядок.

### 3–5. Очереди сообщений — 2026-08-08

- Освоен `k_msgq`: `k_msgq_get()` пишет данные по указателю, а `0` — код успеха.
- При переполнении `K_NO_WAIT` возвращает ошибку; `k_msgq_purge()` явно
  отбрасывает устаревшие сообщения.

### 6. Mutex — 2026-08-09

- Mutex защищает критическую секцию; Zephyr допускает рекурсивный захват
  владельцем, но каждому lock соответствует unlock.

### 7. Semaphore — 2026-08-22

- Semaphore передаёт событие, а не данные; максимум 1 объединяет сигналы.

### 8–10. Таймеры и workqueue — 2026-08-22

- Callback `k_timer` выполняется в контексте прерывания и должен быть коротким.
- `k_work_submit()` переносит работу в system workqueue; долгий handler
  задерживает другие её задачи.

### 11–15. DeviceTree и Kconfig — 2026-08-22

- Kconfig определяет параметры сборки, `prj.conf` задаёт `CONFIG_*`.
- DeviceTree описывает оборудование; освоены `DT_CHOSEN`, `DT_ALIAS`,
  `DT_NODELABEL`, `DT_PROP` и `DEVICE_DT_GET`.

### 16–18. Heap и FIFO — 2026-09-03

- `k_heap_alloc(..., K_NO_WAIT)` возвращает указатель или `NULL`.
- `k_fifo` передаёт указатели без копирования; владелец меняется producer →
  FIFO → consumer.
- Ранний free создаёт use-after-free, отсутствие free — утечку памяти.

### 19–20. Slab и FIFO — 2026-09-19

- `k_mem_slab` даёт пул одинаковых блоков без фрагментации heap.
- Пул из четырёх блоков ограничивает число одновременно выделенных сообщений.
- Consumer возвращает блок через `k_mem_slab_free()`.
- В проверенной реализации исправлен счётчик consumer. При отказе allocation
  producer должен применить retry-policy с задержкой, чтобы не создавать busy loop.
